Follow the same example as getting-started.md: cache a promotions response, then cache a product and invalidate it when its price changes.

1
Cache a promotions response

Fetch twice to see the second request served by Output Cache.

GET /api/promotions Domain: promotions …
2
Cache a product response

The GET caches the product in Data Cache and its HTTP response in Output Cache.

GET /api/products/42 Domain: catalog …
3
Update the product price

The PUT writes the new price and invalidates products/42 in Output Cache and Data Cache.

PUT /api/products/42 Invalidates: catalog/products/42

Suggested: promotions twice → product twice → update price → product once. The final GET is a server MISS and returns the new price. Keep Disable browser HTTP cache checked to see server OC/DC clearly.

See how one endpoint keeps separate cache entries by response representation and selected query values. Change Accept or lang to create a new variant; tracking parameters are ignored.

GET /api/vary-demo Domain: vary-demo …

Suggested: fetch twice → change lang → MISS → switch to XML → MISS → add only utm_source → HIT for the same language and representation.

POST Output Cache via endpoint identity (domain product-search). Search uses a named contract (q + sort + page); uiHint is ignored by identity (must not fragment the cache). Create shares the domain but has no identity binding — not Output Cached.

POST /api/demo/search Domain: product-search …

Suggested: Search twice (OC-HIT) → change only uiHint → Search once (still HIT) → change q or page → MISS → Create (never OC-HIT).
